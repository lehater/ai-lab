# AI Lab — запуск с USB: S0 → S1

**Инструкция для оператора.** Начните здесь на новой машине, не требуется помнить
команды из чата. Проверенная платформа: Ubuntu 24.04 Desktop, amd64, VMware.
S0 восстанавливает прокси и Git; S1 настраивает доступ к GitHub и проверяет хост.
**Первый модуль S1 (GitHub SSH) принят в PR #5; весь этап S1 ещё не завершён.**

## 0. Подготовить флешку на доверенной машине (до развёртывания)

Копируйте **весь каталог `bootstrap/`**, не переименовывая папки.
На флешке должны быть:

```text
USB/
└── bootstrap/
    ├── README.md                     ← вы здесь
    ├── stage0/
    │   ├── bootstrap.sh              ← запускается первым
    │   ├── README.md
    │   ├── proxy/
    │   └── private-proxy/            ← приватные файлы, НЕ в Git
    │       ├── README.md
    │       ├── v2rayN-linux-64.deb
    │       ├── v2rayn-data.tar.gz
    │       └── v2rayn-data.sha256
    └── host/
        ├── bootstrap.sh
        └── README.md                 ← детали S1
```

Три файла в `private-proxy/` берутся из **защищённого локального хранилища**,
а не из GitHub. Их подготовка: [private-proxy/README](stage0/private-proxy/README.md).
В них есть секреты: не выкладывайте наполненную флешку или архив в Git.
**После изменения репозитория флешка сама не обновляется.** На доверенной
машине возьмите принятую версию `main` и обновите содержимое USB, например:

```bash
cd ~/projects/ai-lab
git switch main
git -c http.proxy=http://127.0.0.1:10808 pull --ff-only origin main
USB="/media/$USER/ИМЯ_ФЛЕШКИ"  # замените на фактическую точку монтирования
mkdir -p "$USB/bootstrap"
cp -a bootstrap/. "$USB/bootstrap/"
test -f "$USB/bootstrap/README.md"
test -f "$USB/bootstrap/stage0/bootstrap.sh"
```

Это **копирование с сохранением существующих файлов**, а не очистка
каталога: приватные файлы в `USB/bootstrap/stage0/private-proxy/`
не должны удаляться. Не применяйте `rsync --delete` к этой папке.
Проверьте, что три приватных файла на месте перед запуском S0.

## 1. На чистой Ubuntu — запустить S0 с USB

Подключите флешку. Чтобы узнать путь (метка флешки отличается на машинах):

```bash
find "/media/$USER" -type f -path '*/bootstrap/stage0/bootstrap.sh' -print
```

Запустите найденный файл, **подставив фактический путь**, например:

```bash
bash "/media/$USER/ИМЯ_ФЛЕШКИ/bootstrap/stage0/bootstrap.sh"
```

Что происходит: офлайн установка v2rayN, восстановление прокси, настройка
автозапуска, APT и Git, затем клонирование репозитория в
`~/projects/ai-lab`. **При запросе скрипта откройте v2rayN в GNOME,
выберите рабочий сервер и дождитесь запуска Xray, только потом нажмите Enter.**
Это обязательное ручное действие для первого запуска.

Продолжайте **только** после сообщения `Stage 0 PASS`.
При ошибке остановитесь и исправьте её; не переходите к S1.

## 2. Перейти в каталог кода (после S0)

```bash
cd ~/projects/ai-lab
```

После S0 репозиторий уже клонирован из принятой ветки `main`.
В нём должны быть `Makefile` и `bootstrap/host/bootstrap.sh`.
Проверьте их наличие, прежде чем переходить к S1:

```bash
test -f Makefile && test -f bootstrap/host/bootstrap.sh
```

Если проверка не прошла, остановитесь: возможно, с USB или из старого
локального клона получена устаревшая версия репозитория. Не переключайтесь
самостоятельно на экспериментальную ветку.

## 3. Установить инструменты S1 и проверить повторный запуск

В S0 `make` ещё может отсутствовать, поэтому **первый раз используйте Bash**:

```bash
bash bootstrap/host/bootstrap.sh
```

Далее используйте единый интерфейс:

```bash
make help
make host-setup
make host-setup
make host-test
```

Ожидается `S1 local config and proxied HTTPS: PASS` и **две строки `PASS`**
от `make host-test`. Повторный `host-setup` не должен повреждать настройки.

## 4. Авторизовать SSH в GitHub

```bash
make github-setup
```

Мастер проверит существующий SSH-ключ; **новый создаст только после
подтверждения**. При создании рекомендуется задать passphrase. Мастер
показывает **только публичный ключ**, пытается скопировать его в буфер
обмена и открыть https://github.com/settings/keys. Добавьте **публичный**
ключ в GitHub: `New SSH key` → `Authentication Key`. Затем нажмите Enter
в терминале для проверки (или введите `skip` и проверьте позднее).

Перед первым подтверждением подлинности SSH-сервера сравните показанный
отпечаток с [официальными отпечатками GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints).
**Для офлайн-сверки:** опубликованный GitHub отпечаток **Ed25519** на
2026-10-21 — `SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU`.
Не подтверждайте несовпадающий ключ; при изменении серверного ключа
проверьте актуальное значение из независимого доверенного источника.
Мастер не отключает эту проверку.
Если браузер не открывает GitHub, его прокси нужно настроить отдельно;
успешная работа APT и терминала этого не гарантирует. Если буфер обмена
недоступен, просто скопируйте текст публичного ключа.

После регистрации ключа (если пропустили проверку в мастере):

```bash
make github-verify
make host-verify
```

Ожидается сообщение GitHub об успешной аутентификации и
`S1 GitHub SSH authentication: PASS`. Ответ GitHub `does not provide shell
access` — **нормальный**, у GitHub нет интерактивной SSH-оболочки.

## 5. Перезагрузить и повторить проверку

```bash
sudo reboot
```

После входа в GNOME **не запускайте v2rayN вручную**, чтобы проверить
автозапуск. Затем:

```bash
cd ~/projects/ai-lab
make host-verify
make github-verify
```

Обе проверки должны пройти. Если прокси требует ручного запуска после
перезагрузки, это дефект/ограничение, а не успешная проверка автозапуска.

## Если что-то не сработало

- Не найдены скрипты или приватные файлы: проверьте **структуру USB**
  и [требования S0](stage0/README.md).
- `Stage 0 PASS` отсутствует: сначала исправьте S0.
- Нет `make`: выполните `bash bootstrap/host/bootstrap.sh` из каталога
  репозитория после S0.
- SSH не авторизуется: проверьте регистрацию **публичного** ключа,
  правильность отпечатка сервера и `make host-verify`.
- Для диагностики и подробностей используйте [S1 README](host/README.md).
  Статус и результаты испытаний фиксируются в
  `docs/project/state.md` в репозитории.

## 6. S1-D — Docker (первый принятый модуль)

После успешного S0 → S1 из принятой ветки `main` можно
установить Docker Engine/Compose с прокси **демона Docker** через Xray.
В каталоге `~/projects/ai-lab`:

```bash
make docker-test
make docker-setup
make docker-setup          # повторная проверка
make docker-verify
make docker-pull-test
make docker-compose-test   # временный сервис без публикации портов
```

См. [Docker README](docker/README.md). Обычные сети Compose
используются по умолчанию; строгая контейнерная egress-изоляция
не входит в базовый модуль (D-011).
Оцените доступ из LAN перед публикацией портов приложений.
После слияния обновите `bootstrap/` на флешке из `main`,
сохранив локальные секреты `private-proxy/`.

**Безопасность:** приватные SSH-ключи не отправлять в чат и Git;
`private-proxy` не публиковать. Откат снимка VMware может уничтожить
новый SSH-ключ — сохраните его защищённо либо создайте новый и отзовите
старый ключ в GitHub. AI-компоненты здесь ещё не устанавливаются. Владелец подтвердил
полный цикл S0 → S1 → S1-D из восстановленного `vmware-tools-ready`
с успешными конечными проверками. Этот результат не означает
полностью автономную установку или проверенную из LAN изоляцию.

## 7. Финальная проверка воспроизводимости S0 → S1 → S1-D

**Статус:** владелец выполнил полный прогон после восстановления
`vmware-tools-ready` и сообщил успешные конечные проверки. Этот
раздел остаётся воспроизводимой инструкцией для повторных прогонов.

**Цель:** подтвердить установку из исходного состояния VMware,
а не повторно тестировать уже настроенный Docker. Это контрольный
прогон *оператора*, не полностью автоматическая установка: первый
запуск v2rayN, SSH-ключи и подтверждение GitHub остаются ручными.

### До восстановления снимка — на рабочей системе

1. Убедитесь, что сохранён отдельный **снимок текущего работающего
   `lab-test`** с Docker/S0/S1, например
   `S1D-Docker-Verified-Before-Replay`. Проверьте, что видны **оба**
   снимка: рабочий и исходный `vmware-tools-ready`. Не удаляйте
   рабочий снимок. Более безопасная альтернатива — **клон** исходного
   снимка с отдельным именем виртуальной машины.
2. Подготовьте актуальную USB-флешку из **принятого `main`** по шагу 0
   этой инструкции, сохраняя три приватных файла в
   `bootstrap/stage0/private-proxy/`. Прочитайте этот runbook
   **до отката**: локальный Git-репозиторий, Docker, конфигурация Xray
   и SSH-ключ, появившиеся позже исходного снимка, могут исчезнуть.
3. При потере SSH-ключа из более нового снимка **не восстанавливайте
   приватные ключи из Git или чата**. Новый ключ создаётся только после
   согласия владельца и регистрируется как публичный ключ в GitHub.
   Старые больше не используемые ключи можно позже отозвать в GitHub.
4. Выполняйте восстановление/клонирование **только `lab-test`**,
   не меняя вручную настроенную эталонную VM `lab`.

### Чистая VM — установка в зафиксированном порядке

После восстановления `vmware-tools-ready` войдите в GNOME и
подключите USB. Найдите файл, не угадывая имя флешки:

```bash
find "/media/$USER" -type f -path '*/bootstrap/stage0/bootstrap.sh' -print
bash "/media/$USER/ИМЯ_ФЛЕШКИ/bootstrap/stage0/bootstrap.sh"
```

Замените `ИМЯ_ФЛЕШКИ` на реальную точку монтирования.
При первом запуске откройте v2rayN в GNOME, выберите действующий
сервер и дождитесь Xray, затем нажмите Enter в S0. Переходите дальше
**только после `Stage 0 PASS`**.

```bash
cd ~/projects/ai-lab
git branch --show-current
git rev-parse HEAD

bash bootstrap/host/bootstrap.sh
make host-setup
make host-setup
make host-test

make github-setup
make github-verify
make host-verify

make docker-test
make docker-setup
make docker-setup
make docker-verify
make docker-pull-test
make docker-compose-test
```

После S0 ожидается ветка `main`, а вывод `git rev-parse HEAD`
фиксирует **точную ревизию** всей проверки. `github-setup` может
потребовать создать SSH-ключ, добавить **только публичный ключ**
в GitHub, сверить отпечаток SSH-хоста и подтвердить продолжение.
После каждого этапа при ошибке **остановитесь**, не маскируйте её
ручными изменениями, и запишите на каком шаге произошёл сбой.
Принятые PASS-сообщения для каждой команды описаны выше и в
[Docker README](docker/README.md).

### Проверка после перезагрузки

```bash
sudo reboot
```

После входа в GNOME **не запускайте v2rayN вручную**:
это проверка ранее настроенного автозапуска.

```bash
cd ~/projects/ai-lab
make host-verify
make github-verify
make docker-verify
make docker-pull-test
make docker-compose-test

sudo docker ps --format 'table {{.Names}}\t{{.Ports}}'
sudo ss -lntp | grep -E ':(2375|2376|10808)[[:space:]]' || true
```

Проверки портов дают **только локальную картину на этот момент**;
они не являются внешним LAN-сканированием. При необходимости LAN
проверяется отдельно, с другой машины и под конкретный сервис.

### Что сохранить как доказательство

Сохраните *не содержащую секретов* сводку: исходный снимок/клон,
платформа Ubuntu/VMware, ревизия `git rev-parse HEAD`, факт первого
ручного запуска Xray, все итоговые `PASS` или ошибки, версии
`docker --version` и `docker compose version`, результат перезагрузки,
временные опубликованные порты и незавершённые проверки.

**Не публикуйте** исходные архивы Xray, URL подписок, SSH private key,
авторизационные данные или полный терминальный лог без проверки на
секреты. Результат и ограничения затем отражаются в
`docs/project/state.md` через обычный PR.

**Критерий приёмки:** последовательный проход от указанного чистого
снимка до Docker/Compose, повторной установки и проверок после reboot,
без незафиксированных исправлений. Даже успешный результат не
означает автоматизацию первого GUI-запуска, принудительную
прокси-изоляцию приложений или проверенную LAN-изоляцию.
