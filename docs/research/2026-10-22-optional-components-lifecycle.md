# Опциональные компоненты и воспроизводимые окружения AI Lab: управление без собственной платформы

> **Исследовательский вопрос:** как оператору и AI-агенту выбирать, воспроизводимо применять, проверять и безопасно отключать инструменты Ubuntu VM и исследовательские окружения преимущественно штатными форматами и средствами?
>
> **Статус:** EXPLORATORY — предложение для обсуждения, **не** ADR, не принятое изменение архитектуры.
>
> **Срез:** 2026-10-22. Документация mise на момент проверки обозначает v2026.10.17, Task — v3.54.0; для остальных продуктов фиксируется дата проверки официальных документов, а не утверждается единая протестированная версия.
>
> **Метод:** read-only аудит ветки main, официальной документации и исходных репозиториев; сравнительная инженерная оценка. **Не выполнялись** установка, bench, обновления, очистка, проверка совместимости на lab-test или тестирование безопасности. Обозначения: **[Ф]** факт из первоисточника, **[А]** инженерный анализ, **[Г]** гипотеза/непроверенное свойство конкретного стенда.

## 1. Problem и Scope

**[Ф, R1–R5]** Принятая стратегия определяет сценарно-независимое Infrastructure Core, подключаемые модули, версионируемые шаблоны сред и независимые проекты. Это логические границы, не обязательные программные классы или службы. В main S0 → S1 → S1-D подтверждены оператором в определённом объёме на Ubuntu 24.04 Desktop / VMware (amd64), с ручными этапами; S2–S4 не имеют подтверждённой реализации. Существующий Makefile — компактный интерфейс к bootstrap-скриптам, а не инфраструктурный оркестратор. D-011 оставляет обычные Compose-сети по умолчанию.

**Проблема [А]:** при добавлении Codex, VS Code, n8n, SDK и исследовательских сервисов стоимость ручного применения, настройки, обновления, удаления и воспроизведения растёт. Нужны воспроизводимые *контракты желаемого состояния*, но **не обязательно единая технология** для машины, рабочего пространства и работающего приложения.

**Дополнительные критерии владельца (2026-10-22) [А]:** (1) минимизировать **суммарную цену владения и вынужденных миграций по мере роста**, а не только начальное число инструментов; (2) при сопоставимой технической пригодности отдавать дополнительный приоритет инструментам, широко применяемым в профессиональной среде и востребованным в вакансиях: освоение одновременно создаёт переносимые карьерные компетенции. Допустима небольшая начальная сложность ради долгоживущих стандартных деклараций. Вместе с тем «взять на вырост» означает выбрать расширяемую **модель конфигурации**, а не устанавливать ненужный сегодня постоянно работающий control plane. Из этих требований **не следует** заранее выбирать Ansible, mise, Kubernetes или собственный менеджер.

**Границы:** Ubuntu внутри VMware — целевой host AI Lab. Windows/физический компьютер — платформа виртуализации, не цель установки. Дополнительная VM — отдельный вариант изоляции; отдельные исследовательские проекты — потребители лаборатории. Никаких правок bootstrap, Makefile, state, roadmap, decisions и работающего окружения в рамках этого исследования. Изучаются *конфигурация и размещение*, а не выбор AI-моделей.

### Три независимые оси

| Ось | Вопрос | Примеры |
| --- | --- | --- |
| **Размещение** | Где выполняется компонент? | Ubuntu guest / контейнер проекта / другая VM |
| **Управление жизненным циклом** | Кто применяет, проверяет, обновляет и отключает состояние? | apt/mise/Ansible / Compose / Dev Container CLI / VMware |
| **Владение декларацией** | Где живут конфигурация и операционные доказательства? | ai-lab для общего хоста; отдельный Git-репозиторий потребителя; переиспользуемые примеры по подтверждённой потребности |

**[А]** Нельзя называть образ контейнера «модулем», а каталог Compose — «оркестратором», не определив, какой именно объект и состояние ими управляются. Слова Module / Blueprint / Environment допускаются как предметные обозначения, но **не** обосновывают собственной схемы/DSL.

### Три разных гарантийных контракта

1. **Окружение:** версии, источники артефактов, параметры, зависимости, команды применения, фактическая проверка и очистка. Git + lock/pin повышают повторяемость, но не гарантируют доступность источников, совместимость или побитовое совпадение.
2. **Данные:** отдельные тома/bind mounts, транзакционно согласованные backup, секреты шифрования, retention и успешный restore. Сохранение named volume при пересоздании контейнера ≠ backup.
3. **Работающий сервис:** порядок старта, readiness/health, сеть, доступ, миграции схемы, наблюдаемость, восстановление после reboot и после аварии. Docker healthy ≠ бизнес-операция успешна.

## 2. Alternatives — классы решений, вход и результат

| Класс | Инструменты | Вход → выход / ответственность | Граница |
| --- | --- | --- | --- |
| Bootstrap и управление Ubuntu | существующие Bash + APT; **mise bootstrap**; **Ansible** | Объявления пакетов/файлов/сервисов + права → состояние гостевой ОС | Не заменяют резервное копирование и изоляцию исследовательского процесса |
| CLI/runtime инструментов | **mise [tools]**, lockfile; альтернативно стандартный APT | Версии инструментов → исполнимые runtime в user/system scope | Не эквивалент настройке kernel/AppArmor или полноценному lifecycle ОС |
| Запуск контейнерных приложений | **Docker Compose** | YAML + образы + inputs → сервисы, сети, mounts | Не гарантирует durable backup, restore и security policy |
| Рабочая среда проекта | **Dev Containers Spec**, devcontainer CLI, **DevPod** | devcontainer.json (+ Dockerfile/Compose/Features) → workspace | Не является универсальным менеджером host software или долгоживущих сервисов |
| Операторский вход | существующий **Make**, альтернативно **Taskfile** или mise tasks | Имена задач/аргументы → вызов других систем | Команда «install» сама по себе не задаёт желаемое состояние |
| Декларативный пользовательский стек | **Nix + Home Manager** | Nix expression/flakes/lock → поколения пользовательской среды | Добавляет отдельный package store/экосистему на существующую APT-VM |
| Контрольная плоскость/каталог | DevPod как workspace tool; Coder/Coolify/Komodo/Portainer из R6 | Шаблоны + control plane → централизованные workspace/deployment | Дополнительные состояния, зависимости, операционная цена; не требуются априори |
| Более сильная изоляция | отдельная VMware VM | Готовая базовая VM/снимок → независимая ОС/ядро и диск | Выше расходы и отдельная воспроизводимость для каждой VM |

**[А]** Это не восемь взаимозаменяемых платформ: выбор host provisioner не заменяет Compose, а удобный task runner не снимает требования к жизненному циклу.

## 3. Важное уточнение: mise в октябре 2026

**[Ф, F1–F7]** В официальной документации mise v2026.10.17 существует не только менеджер версий и задач, но и **mise bootstrap**: пакеты (включая apt и сторонние APT sources с проверкой fingerprint), system files/directories, сервисы, Linux users/groups, firewall, Compose, репозитории, пользовательские конфигурации, секретные входы и команды plan/status/apply. Действия bootstrap выполняются **явно**, а не автоматически при чтении конфига.

**[Ф, F2]** Machine modules — файлы вида mise.codex.toml или config.codex.toml, подключаемые через **config environments**. В локальном miserc.local.toml можно выбрать список env; разовый запуск возможен через -E. Несколько модулей комбинируются; конфликтующие ключи разрешаются порядком среды, поэтому пересечения требуют ревью. Plan JSON включает происхождение ресурсов. Это штатный вариант «опционального состава» *без собственного каталога и DSL*.

**[Ф, F3–F5]** Есть отдельные границы, которые нельзя замалчивать:
- mise bootstrap unapply удаляет управляемые файлы, директории (только пустые), user services и dotfiles; **не удаляет APT-пакеты, исходные репозитории, Compose-проекты, accounts, system services и firewall state автоматически**. Изменённые вручную ресурсы защищены, если не применить force. Конфиг модуля нужно сохранять до cleanup.
- Для apt удаление записи **не удаляет пакет**, не удаляет подключённый APT source и не гарантирует возможность установить старую pinned версию, если её уже нет в репозитории. Удаление/очистка apt и sources — явные управляемые операции.
- Для Compose mise поддерживает state running/stopped/absent, status/dry-run, config-hash drift, health и зависимость от пакета/файла/сервиса. Для удаления нужно **сначала** задать state absent и применить, а уже потом удалить декларацию. down_volumes уничтожает тома и по умолчанию false.

**[Ф, F27]** mise поддерживает **`mise bootstrap remote`**: inventory `[bootstrap.remote.hosts]`, выбор отдельных хостов или тегов, передачу bootstrap-проекта через SSH, выбор `mise_env` для каждого хоста. По официальной документации обработка выбранных хостов **последовательная**, возможен `--fail-fast`. Remote `--dry-run` всё равно подключается и передаёт исходники/размещает mise для инспекции хоста: это **не** offline/no-touch проверка. Входной каталог нужно фильтровать от приватных файлов через `exclude`; копирование проекта на чужой хост является отдельной границей доверия. Следовательно, **увеличение числа VM само по себе не вынуждает переходить с mise на Ansible**, но параллельное обновление, оркестрация больших парков и качество отдельных OS modules требуют отдельного сравнения.

**[Ф, F6–F7]** mise.lock фиксирует разрешённые версии/артефакты инструментов (с платформенными границами); это **не** offline-репозиторий или lock-файл состояния всей Ubuntu. Задачи mise выполняются с контекстом инструментов, могут иметь свои tools/env/dependencies; bootstrap task запускается при каждом bootstrap и должен сам быть безопасным при повторе. Для root-операций mise использует sudo/run0/doas по настройке; наличие привилегий не означает безопасность произвольного конфига. Требуется доверенная конфигурация.

**Вывод [А]:** прежний бинарный выбор «mise только для языков, Ansible — для хоста» **устарел**. mise становится серьёзным кандидатом на **optional host provisioning на одной или нескольких Ubuntu VM**. Однако документированные частичный unapply, новая по времени функциональность и пересечение с принятыми Bash/Compose не позволяют назвать его автоматически выбранным инструментом или доказанно надёжным в AI Lab.

**Пояснения [Ф/А]:**
- **Ansible [F8–F10, F28]:** roles, role dependencies и tags структурируют пакетные сценарии; ansible.builtin.apt поддерживает state=absent, purge/autoremove. **Исключение роли из playbook или отказ от тега не удаляет ранее установленные ресурсы**: для этого нужны явные состояния `absent`, правила ownership и безопасный cleanup; `autoremove` затрагивает и общие зависимости, поэтому применяется осознанно. `--check --diff` — симуляция только для поддерживающих её модулей, а не транзакция или гарантия корректного полного плана. Ansible collections — механизм дистрибуции roles/plugins, а не обязательный слой для нескольких локальных ролей. Одна Ubuntu VM допускает `connection: local`; при нескольких VM — привычные inventory, host_vars, ограничение целей, стратегии и параллельные forks с риском гонок в общих ресурсах.
- **mise [F1–F7, F27]:** ресурсы применяются последовательными фазами с частичной идемпотентностью, `bootstrap` **не транзакционен**: после ошибки предыдущие изменения остаются. Machine modules и SSH inventory позволяют расти от одной VM, но штатный `unapply` неполный, а `apt` не удаляется автоматически при отключении env. Сравнение эксплуатационной зрелости mise bootstrap 2026 с Ansible не является тестом длительного сопровождения.
- **Compose [F11–F14]:** profiles включают сервисы в *одном Compose application*, depends_on задаёт запуск зависимостей, но это не общий межпроектный dependency manager. Compose include/merge дают повторное использование, но merge имеет правила порядка и относительных путей. Раздельный project name уменьшает коллизии и blast radius. docker compose config -q проверяет конфигурацию, но не эксплуатационные инварианты.
- **Dev Containers [F15–F17]:** devcontainer.json, Features, Dockerfile и Docker Compose описывают рабочий контейнер; reference CLI поддерживает up/build/exec/read-configuration. Стандарт разрабатывает **workspace**, не весь production deployment. DevPod — CLI/provider над этим стандартом; добавляет управление экземплярами и может удалить VM/container по provider, что требует проверки persistence policy.
- **Task [F18]:** includes/namespaces и list дают масштабируемые имена; status и deps помогают исполнять скрипты, но не заменяют проверку декларативного состояния. Сменять имеющийся Make только ради сокращения числа строк — недостаточная причина.
- **Nix/Home Manager [F19]:** поколения, переключение/rollback и пользовательские пакеты дают более строгую модель инструментов; на принятой Ubuntu 24.04 добавляется вторая package/runtime модель, а systemd/AppArmor/apt остаются отдельной работой. Не оправдано как первый шаг одного стенда.

### 4.1. Professional Adoption & Career Relevance — дополнительный критерий выбора

**Назначение [А]:** среди **уже технически пригодных** вариантов предпочитать широко применяемый на реальных проектах инструмент, когда это снижает риски поиска решений/сопровождения и позволяет изучить переносимый навык, востребованный работодателями. Оцениваются **два разных сигнала**: adoption профессиональным сообществом и **прямой спрос в вакансиях**. Это не эквивалентные величины, их нельзя механически сложить в один рейтинг.

| --- | ---: | --- | --- |

| Nix | **5,7%** (622) | Сопоставимого показателя не извлечено | Показатель относится именно к Nix, **не** к Home Manager |
| **mise bootstrap** | **Нет отдельной категории** | **Нет сопоставимого показателя** в использованном срезе | **Неизвестно**, а не «нулевая популярность» или доказанное отсутствие вакансий |

**Границы достоверности [Ф/А]:**
- Stack Overflow [F29] — добровольная международная выборка разработчиков разных ролей (строка *All Respondents*); это **не** доля всех профессионалов, DevOps-команд или вакансий. Docker / Compose объединены в одной строке опроса. Для Ansible и mise нет пары «два числа из одной репрезентативной выборки».
- DevOpsHunt [F30] — агрегатор объявлений со своей выборкой, фильтрами и AI-извлечением навыков; цифры отражают **его активные объявления**, а не мировой рынок. Один пост может содержать несколько инструментов; Docker и Compose нельзя считать единым показателем вакансий, а отсутствие mise в топе не даёт нулевого значения.
- GitHub Stars, число скачиваний и контрибьюторов допустимы лишь как **вспомогательные прокси community activity**: звёзды не равны production adoption, а скачивания могут отражать CI и автоматические обновления. Для подтверждения рынка труда нужен опрос или выборка вакансий с указанными датой, географией, ролью, знаменателем и поисковой методикой.
- При сравнении на узком рынке (например, конкретная страна или роли AI Infrastructure/DevOps/Platform Engineer) востребованность следует переоценить в **той же** выборке и с точными названиями: \`mise\` неоднозначно для текстового поиска, а \`Docker\` и \`Docker Compose\` не эквивалентны.

**Порядок принятия решения [А]:**
1. **Жёсткие ограничения:** ответственность инструмента, безопасность, воспроизводимость, приемлемый lifecycle/cleanup, соответствие Ubuntu/VMware и независимым проектам. Неисправимый пробел здесь нельзя компенсировать популярностью.
2. **Инженерный горизонт:** стоимость внедрения, drift, обслуживания, миграции и выхода с технологии на 2–20 опций / несколько VM.
3. **Tie-break / дополнительная ценность:** при сопоставимых (1) и (2) предпочитать инструмент с **подтверждённой** профессиональной востребованностью и развитой экосистемой. Отсутствие данных для менее известного инструмента фиксировать как неопределённость, а не штраф 0 баллов.
4. **Проверка актуальности:** для ADR отдельно обозначить целевые вакансии/рынок; карьерный эффект является **прикладным дополнительным критерием**, а не формальным обещанием трудоустройства.

**Применение к спору mise ↔ Ansible [А]:** Ansible получает **дополнительное преимущество по подтверждённому спросу** на навыки автоматизации инфраструктуры, но это **не доказательство количественного превосходства над mise**, поскольку для mise нет сопоставимой рыночной метрики. Не следует ради «популярности» внедрять Kubernetes, Terraform или второй host-manager, если они не решают конкретный инфраструктурный вопрос.

## 5. Модели размещения и ownership

### A. Host-managed (Ubuntu VM)

**Назначение:** общие инструменты, доступные из GNOME/терминала, и настройки ОС, влияющие на kernel/security/daemon. **Вход:** подписанные package sources, версия, права, policies, пользовательская конфигурация. **Выход:** установленный и диагностируемый компонент в Ubuntu.

**[А]** Системные GUI-программы и AppArmor — естественные host-managed объекты. Глобальные SDK и npm-пакеты требуют обоснования: они увеличивают общий mutable state и могут конфликтовать между экспериментами. Для host операций важны управление root-правами, версиями источников, проверка фактической политики и явный teardown. Установка cli в HOME не делает его sandbox независимым от ядра.

**Реалистичные альтернативы:** (1) продолжать Bash/APT install/verify для принятого S0/S1/S1-D и не добавлять новых host options; (2) **с первого следующего host option** принять mise machine modules; (3) **с первого следующего host option** принять Ansible local playbooks/roles. При выборе между (2) и (3) сравнить в одном контексте Codex sandbox policy, VS Code APT, 2–20 дополнительных инструментов и возможность нескольких VM. Не включать сразу mise и Ansible как двух владельцев одних пакетов/файлов.

### B. Project-managed / isolated containers

**Назначение:** зависимости конкретного исследования, SDK, CI/workspace tools и контейнерные сервисы. **Вход:** Git + lockfiles + devcontainer.json/Dockerfile/Compose + секреты вне Git. **Выход:** отделяемое рабочее пространство и/или сервисный стек.

**[А]** Для процесса разработки — Dev Containers; для работающего сервиса — Compose. Они могут сосуществовать: devcontainer ссылается на Compose и открывает service/workspace внутри стека. DevPod не обязателен, если reference CLI или VS Code уже обеспечивает нужный workflow. Сервисы с долгоживущими данными следует эксплуатировать отдельно от уничтожаемого workspace, если жизненные циклы отличаются.

**Ограничения:** Docker socket/control доступа даёт большие полномочия; изоляция контейнера — не security boundary для недоверенного root/privileged workload. Исследовательские зависимости в контейнере не требуют host-модификаций, пока не нужны драйверы, kernel hooks, устройства или daemon integration.

### C. Separate VM

**Назначение:** изоляция несовместимых системных политик, root-sensitive/runtime компонентов или потенциально опасных экспериментов. **Вход:** версионированная базовая VM/снимок, bootstrap, ограничения ресурсов, network policy. **Выход:** независимо удаляемая ОС.

**[А]** Оправдано при конфликтующих конфигурациях AppArmor/namespace/драйверов, ином уровне доверия, требованиях к ядру или проверке чистого rollback. Контейнер предпочтительнее для обычных SDK/сервисов. VMware snapshot полезен как тестовый reset, **не заменяет off-VM backup и восстановление данных**. Двойная иерархия VM + контейнеры должна иметь реальную причину.

**Codex security [Ф, F20–F22]:** текущая реализация Codex Linux sandbox использует bubblewrap и namespaces/seccomp; на Ubuntu AppArmor может запрещать создание user namespace. Нельзя считать установку npm/CLI достаточной проверкой. Ошибка AppArmor **не является основанием глобально отключить защиту**: targeted policy и проверка действующей изоляции безопаснее, чем отключение системных sysctl. Конкретная совместимость версии Codex, системного bwrap, Ubuntu 24.04 и имеющихся AppArmor profiles — **[Г] локальная**, а не гарантированная документацией. Пользовательские GitHub issue — сигналы о failure modes, не доказательство для lab-test.

**VS Code [Ф, F23]:** официальный APT repository и пакет существуют, но выбор стороннего источника кода должен явно проверять key/fingerprint/apt provenance. **[А]** Неправильно помещать GUI-редактор в devcontainer, если требование — локальное GNOME-приложение в Ubuntu.

**n8n [Ф, F24–F26]:** актуальная документация предлагает Compose и опциональную конфигурацию n8n Assistant с дополнительным **privileged Docker-in-Docker sandbox-runner**. **[А]** Нельзя без отдельного threat model считать данный пример безопасным минимальным S2-стеком: для smoke достаточно простого n8n без Assistant sandbox либо отдельного безопасного disposable HTTP-сервиса. Даже при PostgreSQL нужно сохранять user state и encryption key. Port publishing по умолчанию ограничить loopback при локальном эксперименте; LAN exposure оценивать отдельно, не заявлять сеть изолированной без теста. Не применять `down -v` без подтверждённого намерения уничтожить данные.

## 7. Как организовать выбор при десятках компонентов без собственного интерфейса

**[А, рекомендация без принятия ADR]** Не хранить всю номенклатуру в корневом Makefile. Единый вход — **документация + стандартные CLI, которыми уже управляют ресурсы**, с несколькими стабильными командами-диспетчерами для bootstrap и проверок при необходимости:

- **Host:** маленькие независимые декларации, сгруппированные штатными mise **config environments** (если mise выбран) или Ansible roles/tags (если он выбран). Локальный выбор состава хранится **вне Git**; повторяемая комплектация требует версионированного примера/зафиксированного перечня выбранных env, а не только личного miserc.local.toml.
- **Container services:** независимый compose.yaml на сервис/продукт или ограниченные profiles внутри *одного* связанного стека; для переиспользования — штатные include/override с проверкой docker compose config. **Не** смешивать все независимые исследования в один гигантский Compose project: профили не являются межпроектной системой.
- **Workspace:** собственный .devcontainer/devcontainer.json рядом с независимым исследовательским проектом; CLI выбора — devcontainer (или DevPod при полезности provider lifecycle).
- **Operator/agent:** показывать доступные host options через версионированный **Markdown-индекс** с ссылками на native module/role; после выбора работать штатными `mise bootstrap plan/status` или `ansible-playbook --list-tags/--check --diff`. Для сервисов `docker compose config --profiles/--services` показывает **состав данного проекта**, а `docker compose ls --all` — известные уже созданные проекты, но **не каталог всех ещё не установленных стеков**. Поэтому для обнаружения *доступных* независимо хранимых стеков нужны ссылки из документации/репозиториев, а не ожидание, что Compose обнаружит всё автоматически. `make help` по-прежнему перечисляет только базовые инфраструктурные команды. Это разные границы — не требуется единое API поверх всех.
- **Composition:** небольшой version-controlled документ «состав среды» может содержать командные инструкции и выбранные native config files без нового машиночитаемого формата. Для одной и той же host-комплектации сохранять перечень env/roles и версии в Git, иначе личный `miserc.local.toml` воспроизводит только конкретную машину. Переиспользуемые Compose/Dev Container артефакты располагаются у их владельца; ссылки на них не требуют переноса всех проектов в ai-lab. Собственная модель Blueprint не нужна, пока штатные декларации достаточны.

### Полный пользовательский сценарий без общего CLI

**[А]** Цель UX — **единая последовательность понятных действий**, не обязательно единая команда для разных типов ресурсов. Доступные декларации публикуются в обычном небольшом Markdown-индексе с колонками «где живёт», «владелец», «что устанавливает», «риски/данные», «ссылка на native file», «как проверить/отключить». Это навигация, **не исполняемый каталог** и не второй источник конфигурации. Git остаётся источником желаемого состояния. Индекс подходит десяткам записей и позволяет агенту обнаруживать доступные опции через обычное чтение Git.

| Этап | Host, если выбран **mise** | Host, если выбран **Ansible** | Изолированный сервис / workspace |
| --- | --- | --- | --- |
| **Discover** | Список `mise.<env>.toml` и краткие описания в Git; `mise tasks ls` только для заданных tasks | Список roles/playbooks в Git; `ansible-playbook --list-tags` **только для реально размеченных задач**, dynamic includes могут не раскрываться | Ссылки на Compose/`.devcontainer` в индексах проектов; нет штатного общего списка незапущенных стеков |
| **Select** | `-E codex` или versioned перечень config environments; не редактировать общий конфиг автоматически | playbook с явно включёнными roles или `--tags codex` при корректной tag-дисциплине | Путь к проекту и native compose.yaml; profiles — только внутри одного стека; devcontainer.json — внутри проекта |
| **Plan** | `mise -E codex bootstrap plan`; для конкретного cleanup отдельный dry-run | `ansible-playbook ... --check --diff` с документированными пропусками; `--list-hosts` перед remote run | `docker compose config`; CLI devcontainer read-configuration/build в применимом режиме; **план запуска не равен dry-run service migration** |
| **Apply** | `mise -E codex bootstrap` из доверенного конфига после просмотра плана | `ansible-playbook` на ограниченном inventory с reviewed roles и необходимым `become` | `docker compose up -d`; `devcontainer up`; approval для privileged mounts / Docker socket |
| **Verify** | bootstrap status **плюс функциональный smoke**, не только «installed» | фактические host tasks/command verification, при необходимости повторная `--check` | `docker compose ps`, health и тест реального API; devcontainer exec / тесты SDK |
| **Disable / remove** | снять env **после отдельного cleanup** APT/Compose/system state; `unapply` только для покрываемых им ресурсов | отдельный reviewed `state: absent` cleanup playbook; снятие тега **не удаляет** пакет | `docker compose stop/down` не равно уничтожению данных; devcontainer delete и политику persisted volumes проверить отдельно; `down -v` только по отдельному разрешению |

**Пример операторского пути (не исполнять в рамках исследования):** прочитать host options в Git → выбрать Codex и VS Code → просмотреть фактический plan/check → получить подтверждение на изменения Ubuntu и AppArmor → применить → проверить Codex sandbox и GUI → сохранить evidence. Для n8n — перейти в **его** проект → validate Compose → запустить → проверить сценарий/данные/backup → по необходимости остановить, сохраняя volume. Агенту по умолчанию разрешён **read-only review**; apply/remove требует явного approval и ограничений прав.

**Граница UX:** ни Ansible, ни mise, ни Compose не предоставляют универсальный discovery для всех чужих Git-репозиториев и VM. Если действительно потребуется интерактивный **единый UI**, это новая потребность с собственной ценой управления; сейчас Markdown-навигация и нативные средства — сознательный компромисс, а не обещание несуществующей функции.

### Иллюстрация механики, а не предлагаемый внедряемый файл

Если выбран mise для host options, официально поддерживаемая идея — раздельные файлы machine modules и список сред:

~~~toml
# Пример, схематично. Не запускался на lab-test.
# ~/.config/mise/miserc.local.toml (НЕ коммитить как общую комплектацию)
env = ["codex", "vscode"]
~~~

~~~sh
# Диагностика/предпросмотр; только пример синтаксиса из официальной модели mise
mise bootstrap plan
mise bootstrap status
mise bootstrap --dry-run

# Действие только после отдельного решения и тестового плана:
# mise bootstrap
~~~

Для **чистого Make + Compose baseline** нового CLI вообще не требуется: оператор переходит в директорию нужного проекта и использует стандартные docker compose config/ps/up/down. Это **осознанный более простой вариант**, а не временный технический долг.

### Три варианта для S2 — стоимость и точка перехода

| Вариант | Новые обязательные зависимости | Цена разработки и поддержки (относительная) | Условие выбора |
| --- | --- | --- | --- |
| **V0: существующие Make/Bash + Compose** | **Нет** | **Низкая** для уже принятого bootstrap/одного S2 Compose-сервиса; при росте *новых host options* migration cost становится высокой | Сохранить для S0/S1-D и сервиса S2; **не** принимать по умолчанию для всей будущей host-серии |
| **V1: mise для *новых* host options; Compose напрямую** | mise, доверенные machine modules и их trust policy | **Средняя** начальная, ниже повторяемость кода; риск при сложном policy lifecycle/частичном unapply | Если ожидаемая host-нагрузка — прежде всего user tools и простые system resources; проверить capability gap по AppArmor/VS Code |
| **V2: Ansible local roles для *новых* host options; Compose напрямую** | ansible-core/collections по необходимости, inventory/roles | **Средняя–высокая** начальная, но потенциально меньше риска *смены класса* OS manager | Если ожидаются system files/AppArmor/apt sources/службы и затем несколько VM; выполнить узкий proof of capability |

**[А]** V1 и V2 — **альтернативы управления одним host scope**, не рекомендуемая совместная установка. Упрощение одного интерфейса нельзя покупать ценой двух независимых владельцев одного ресурса. У V0 возможен низкий старт, но **высокая накопленная миграционная цена**: новые системные host options целесообразно стандартизовать **до** массового появления Bash-модулей. Существующий S0/S1-D не требуется переписывать ни при одном выборе.

### Результат выбора направления после обсуждения (2026-10-22; **не ADR**)

**[А, выбор для следующей инженерной итерации]** Для **новых host-managed компонентов Ubuntu VM** выбран **Ansible Core с локальными Playbooks и Roles** в качестве основного механизма управления конфигурацией. Это **выбранное направление работ**, но ещё **не принятое изменение реализованной архитектуры**: применение к `lab-test`, acceptance-тесты и запись в `decisions.md` требуют отдельных шагов. Документ исследования остаётся EXPLORATORY.

**Почему этот вариант:** Codex + AppArmor затрагивают системную политику, VS Code требует управлять APT source/signing key, а будущие опции будут включать systemd и OS files. Ansible лучше соответствует доминирующему классу задач на перспективу нескольких VM, позволяя начать с локального inventory без централизованного сервера. Профессиональная распространённость и спрос на Ansible — дополнительный положительный критерий, **не замена инженерной пригодности**. mise bootstrap — технически пригодная и более компактная альтернатива; его не требуется внедрять параллельно или проводить второй полноценный proof-of-concept без появления конкретного пробела Ansible.

**Интерфейсы и владельцы (не смешивать):**

| Область | Выбранный/сохранённый механизм | Дальнейшее развитие |
| --- | --- | --- |
| Уже принятые S0/S1/S1-D | Существующий Bash/APT/Make и Docker | **Не мигрировать** без отдельной ценности; Ansible устанавливать **после** работоспособного baseline |
| Новые host options (CLI/GUI, APT sources, AppArmor, systemd) | **ansible-core**; локальный inventory/connection, небольшие роли; `become` только где нужно | Позднее добавлять hosts/groups и vars, сохраняя формат ролей; explicit install/verify/cleanup |
| Отдельные долговременные сервисы | **Docker Compose** непосредственно в owning project | Сохранить Compose YAML, volumes/backup/restore; не оборачивать каждый проект в host-manager |
| Исследовательские рабочие пространства | **Dev Containers** / reference CLI | Независимые devcontainer.json; DevPod по реальной provider-потребности |
| Менеджер пользовательских версий | **Не выбран/не требуется сейчас** | mise `[tools]` допустим в будущем **только** как отдельная область без второго владельца APT/AppArmor |
| Универсальный оркестратор/UI | **Не требуется** | Отдельное обоснование при реальном эксплуатационном дефиците |

**Минимальный проверяемый шаг после отдельного разрешения на реализацию:** на **отдельной проверочной ветке** описать *одну* host role для выбранного небольшого, обратимо удаляемого компонента (например, VS Code APT+GUI, если GUI smoke доступен на lab-test), inventory только localhost, входные версии/источники, `--check --diff` и ограничения preview, реальный setup, повтор, проверку после reboot и явную процедуру cleanup. Измерить число ручных шагов и отсутствие изменения принятой S0/S1-D конфигурации. **Codex/AppArmor** оставить вторым, более чувствительным вертикальным срезом с отдельным negative sandbox test; не ослаблять AppArmor глобально. В этой исследовательской ветке ничего не устанавливать.

**Условие пересмотра выбора:** если первый clean-VM E2E показывает чрезмерную сложность Ansible или конкретную неподдержанную функцию относительно mise bootstrap, зафиксировать недостаток и повторно открыть сравнение **до** масштабирования host options. В противном случае использовать Ansible как единый owner host-state. Нельзя утверждать `VERIFIED` до успешного испытания. После согласования/приёмки оформить ADR с этим выбором и фактическими свидетельствами.

### Горизонт развития, цена смены механизма и критерии выбора

**[А]** Для данного исследования «на вырост» — возможность расширить *первоначальный формат* без неизбежной замены. **TCO** (относительная) = `первичное внедрение + сопровождение деклараций + подтверждение/устранение drift + политика безопасности + восстановление/teardown + ожидаемые изменения при росте + стоимость миграции`. Часы и вероятности миграций не измерялись; ниже дана **качественная инженерная оценка**, а не количественный прогноз.

| Реалистичное развитие | V0 Bash+Make | V1 mise bootstrap | V2 Ansible | Что не должно переезжать |
| --- | --- | --- | --- | --- |
| **2 → 20 host options** (APT, системные файлы, AppArmor, GUI) | Рост повторного кода, ручной проверки idempotence, опасность рассинхронизации; затем вероятная перепись в declarative provider | Env modules и plan снижают дублирование; остаётся явно управлять apt cleanup, внешними службами, policy gaps | Roles, vars, tags, inventory; больше YAML/discipline с самого начала, но стандартный рост OS tasks | Нативные APT repos/ключи, тесты поведения, границы root, данные |
| **1 → 3–10 Ubuntu VM** | Появляется внешний SSH/inventory или копирование сценариев; возможен собственный orchestration glue | **Поддерживается** штатным remote SSH inventory и env per host; последовательно, staging исходников и remote dry-run не no-touch | Inventory/host_vars, local→SSH без смены role format; возможно параллельное исполнение и host limiting, при этом сложнее безопасная эксплуатация | Чистый VM bootstrap и доступ, IaC/verification per host |
| **1 → 10–30 независимых Compose projects** | Не масштабировать root Make до 30 targets; запускать стандартный Compose по проектам | Mise compose допускает декларацию проектов, но не обязателен и создаёт второй lifecycle owner при дублировании | Может запускать Docker через модуль, но в таком случае риск переписать стандартный compose.yaml и удвоить owners | **Compose YAML + project names + volume/backup contracts** независимо от host provider |
| **Один оператор → несколько агентов/операторов** | Bash требует локальной договорённости и прав | machine modules, plan/status/remote удобны; нужно ограничивать trust/privileges, изменения в Git/PR | check/diff/inventory/tags и доступ по SSH/privilege escalation; отдельные approvals, секреты и audit всё равно нужны | Git PR review, ограничение доступа, read-only → approved apply, evidence |
| **Нужно сложное security/hardening policy** | Быстро растут условные скрипты, проверка/cleanup | Возможности files/services/firewall есть; конкретные AppArmor и обратные операции могут потребовать хуков | Более широкий набор OS-модулей и коллекций; политика/откат всё равно должны быть протестированы | Требования безопасности и негативные smoke tests |

**Migration-cost по направлениям [А]:**
- **V0 → V1/V2 поздно:** когда Bash уже содержит десятки разнородных side effects, придётся инвентаризировать unmanaged state, переписать установочные сценарии, определить владельцев и провести re-adoption без повреждения существующих файлов. Чем позже, тем выше риск.
- **V1 → V2:** TOML machine env → роли/variables/tasks YAML с повторной проверкой drift, cleanup и secrets; автоматического стандартизованного конвертера/совместимости нет. **V1 не является «облегчённым Ansible»**, замена будет миграцией формата. Раннее принятие V1 обосновано, только если его capability boundary вероятно достаточен.
- **V2 local → V2 multi-VM:** те же роли/плейбуки при замене/добавлении inventory и SSH-механизма, но задачи могут оказаться host-specific; отсутствие миграции формата **не** гарантирует переноса всех side effects.
- **Compose/Dev Containers:** остаются native форматами и при V0, V1, V2. Смена host-manager **не должна** затрагивать project/workspace templates. Это главный способ снизить будущую миграцию без глобальной платформы.

### Выбор на вырост: критерии, а не порог по количеству машин

| Критерий | V1 mise | V2 Ansible | Предварительная оценка |
| --- | --- | --- | --- |
| **Простой CLI + версии инструментов + machine modules** | Сильная документированная поддержка, единый runtime | OS-конфигурация через roles, версии user tool chain требуют других средств | **mise**, если host options в основном простые |
| **Ubuntu policies, package sources, systemd, AppArmor, безопасное изменение и очистка** | Bootstrap охватывает многие ресурсы; часть cleanup/проверок требует отдельных процедур | Много стандартных модулей, роли, handlers, check/diff (с ограничениями) и явные absent tasks | **Ansible** — предпочтительный кандидат, если это основной тип работ |
| **Несколько VM** | Remote inventory через SSH, последовательно | Inventory+SSH/parallel execution/rollout patterns | **Оба**; количество VM не является самостоятельным решающим критерием |
| **Безопасность / агентный процесс** | Trust, явное apply, dry-run с ограничениями | Inventory, check/diff, become; check mode не всегда симуляция всех действий | **Оба** требуют ограниченных разрешений и независимого verify |
| **Стоимость эксплуатации и зрелость bootstrap-подсистемы на горизонте нескольких лет** | Меньше собственных файлов, но machine bootstrap сравнительно новая область в 2026 | Развитая зрелая экосистема конфигурационного управления, но выше начальные накладные расходы | **Не доказано лабораторными тестами**; оценивать в выбранном реальном сценарии |
| **Professional Adoption / карьерная ценность** | Нет сопоставимой отдельной строки survey/job ads; отсутствие данных ≠ ноль | SO Survey 2026 **12,0%** использования (all respondents); DevOpsHunt **1 043 из 3 785** вакансий | **Плюс Ansible** по подтверждённому спросу, но не прямое количественное сравнение с mise; только после технических критериев [F29–F30] |

**Выбранное направление работ [А, 2026-10-22]:** оставляем подтверждённый S0/S1-D, а **новые host-managed компоненты организуем через ansible-core, local playbooks/roles**. Это консервативное решение на долгосрочный системный scope (APT, AppArmor, systemd, Ubuntu, дополнительные VM); mise bootstrap остаётся проанализированной альтернативой, но **не устанавливается** параллельно. Дополнительный аргумент — подтверждённая профессиональная востребованность Ansible [F29–F30]. Выбор **не равен accepted ADR или VERIFIED реализации**; следующий этап — минимальная обратимая role и независимая clean-VM проверка при разрешении реализации.

**Гейт принятия [А/Г]:** заранее описать **две реальные host options** — Codex CLI + Linux sandbox/AppArmor и VS Code + APT repo/GUI — как один и тот же функциональный контракт и провести read-only architecture comparison: декларации, план/check, sudo, apply/rerun, remove, version pin, сетевой bootstrap, возможный remote execution, maintenance files. Документации достаточно для общей функциональности; **практический clean-VM spike нужен только** для неизвестных деталей интеграции, привилегий и реального sandbox. Не писать в рамках этого исследования оба полноценных provisioning implementation.

## 8. Что изменилось относительно platform-landscape [R6]

| Было исследовано ранее | Что добавлено здесь | Следствие |
| --- | --- | --- |
| Системы уровня Workbench/DevPod/Coder/Komodo/Coolify, их control plane и template catalogs | Границы **host packaging/optional selection** (mise modules и Ansible roles) | Выбор модулей host можно организовать вообще без deployment platform |
| Рекомендация начать Compose baseline на S2 | Конкретные profiles/include, project-scoped ownership, версии/удаление/backup и разделение service vs data | **Подтверждает**, а не отменяет Compose-first для сервисов |
| Dev Containers/DevPod как проектная среда | Стандарт devcontainer.json, Features и самостоятельный CLI без DevPod | DevPod **не обязательная зависимость** для воспроизводимого workspace |
| Reusable templates остаются логическими артефактами AI Lab | Состав окружения может опираться на mise env + compose.yaml + devcontainer.json **без Blueprint DSL** | Возможное уменьшение собственного IaC-кода, не отказ от принятой логической модели |
| Риск drift и утраты данных | Частичный mise unapply, apt/source cleanup, Compose down -v, секреты ключей и executable smoke | Требует явного контракта teardown/recovery на каждый компонент |
| Host bootstrap рассматривается как внешняя предпосылка platform tools | mise bootstrap в 2026 охватывает части OS provisioning **и SSH remote inventory**; Ansible — полноценная альтернатива | **Новая конкуренция внутри host-management**, которую landscape не анализировал |

**Противоречий с D-001, D-002, D-003, D-010, D-011 и roadmap не выявлено [А].** Смена принятого Bash bootstrap или пересмотр места хранения reusable templates **не предлагаются этим документом**. Отдельно: названия Module/Template в стратегии остаются, потому что это логические категории, а не выбор реализации. В ранее предложенном эксперименте одного HTTP-сервиса + PostgreSQL основная идея сохраняется; для вопроса **host optionality** потребуется самостоятельная маленькая проверка, если для неё возникнет конкретная потребность.

### Минимальный следующий E2E, после отдельного согласования

**Первая итерация должна одновременно сохранять перспективу развития и давать работающий результат S2, без внедрения инструмента до решения.** В отдельной implementation PR:
1. Взять **один** disposable Compose service с постоянными данными, отдельным project name, explicit volumes, фиксированным image ref и локальным ограничением опубликованных портов.
2. Сохранить compose.yaml, non-secret inputs и отдельные шаги проверки, backup/restore, teardown. Проверить docker compose config -q, запуск и API smoke.
3. На lab-test из согласованного снимка: первоначальная установка → rerun → reboot → recreate → восстановление из backup после controlled data loss. Зафиксировать Git SHA/версии, все реальные команды, manual steps, PASS/FAIL.
4. **Для следующего host option начать с выбранного Ansible**: одна небольшая роль с локальным inventory, отдельно plan/check и фактический verify, rerun и безопасный cleanup. Практический test — только в следующей согласованной implementation PR на lab-test, **не в этом исследовании**. Mise повторно рассматривать только при доказанном функциональном/эксплуатационном пробеле.
5. **Выбор host manager завершён на уровне направления**: Ansible Core. После согласованного маленького E2E и оценки эксплуатационных свойств подготовить **ADR об уже выбранном решении**, с условиями пересмотра, ownership и exit path. Принять его в decisions только после явного согласия и проверок; не объявлять ранний выбор равным проверенной реализации.

**Критерий успеха [А]:** оператор и агент могут воспроизвести нужный *конкретный* сервис/инструмент без знания переписки, с заданными inputs, фактической проверкой и управляемыми последствиями удаления. Преимущество нового инструмента должно выражаться в уменьшении кода/ошибок/ручных операций, а не в маркетинговом списке функций.

## 10. Findings и рекомендации к решению

1. **[Ф]** mise v2026.10.17 действительно содержит machine modules, bootstrap plan/status/apply, APT sources, files/services и управление Compose. **[А]** Это наиболее содержательный *новый* кандидат на optional host management, не рассмотренный в R6. **[Г]** Его эксплуатационная надёжность на lab-test пока неизвестна.
2. **[Ф]** mise unapply/apt cleanup не обеспечивают полное симметричное удаление. **[А]** Декларация установки, owner данных и инструкция безопасного удаления — разные ответственности. Нельзя считать «отсутствует в выбранном env» равным «удалено».
3. **[Ф]** Docker Compose и Dev Containers уже предоставляют собственные декларации, профили и CLI. **[А]** Универсальная оболочка, каталог Blueprint/Module, ещё один orchestration control plane и Taskfile одновременно **не обоснованы**.
4. **[А]** Для **S2 контейнерных сервисов** оставить **V0: существующие Make/Bash + Compose + Git + независимые verify/recovery**, не расширяя Make до «100 сервисных целей». Для **новых host options выбран Ansible Core + Roles + Playbooks**, начиная с локального inventory, без AWX/control plane. Альтернатива mise документирована, но не внедряется параллельно. Ansible также требует явных cleanup tasks; факт выбора пока не равен принятому ADR или фактическому PASS.
5. **[А]** В проектных средах применять Dev Containers как формат, Dev Container CLI как минимальное исполнение; DevPod, Nix и дополнительные VM вводить по явным сигналам о недостающих функциях. Для нескольких VM **оба** host-кандидата способны работать по SSH; это не критерий автоматического выбора Ansible. **Профессиональное распространение — дополнительный tie-break**, не повод устанавливать технически ненужную платформу. Все обещания воспроизводимости должны иметь clean baseline и тест, не только декларацию.
6. **Статус:** выводы исследования **не приняты**; архитектура, milestone state и код main не изменяются. Практическая реализация — отдельная обсуждаемая задача.
