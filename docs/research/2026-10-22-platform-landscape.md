# Landscape study: среды и платформы для воспроизводимых AI-исследований

> **Статус:** EXPLORATORY / исследование, не архитектурное решение  
> **Дата среза:** 2026-10-22  
> **Объект:** AI Lab `lehater/ai-lab`  
> **Метод:** анализ первичной документации и README проектов; без установки и измерений на `lab-test`  
> **Решение о внедрении:** не принято

## 1. Вопрос и контекст

**Вопрос:** какие готовые инструменты позволяют поддерживать независимую инфраструктурную AI-лабораторию и быстро создавать, развёртывать, проверять и удалять исследовательские AI-окружения? Где заканчиваются зоны ответственности этих инструментов и что действительно необходимо реализовать в AI Lab?

Исходная идея: минимальная воспроизводимая инфраструктура как основание; конкретные AI/agentic/RAG/automation-проекты живут независимо, могут храниться в своих Git-репозиториях и иметь собственные Compose/Dev Container/скрипты/workflow. Предлагаемые в обсуждениях каталоги `Capability`, `Blueprint`, `Scenario` и универсальный `Deployment Workflow` рассматриваются **как гипотезы**, а не принятые требования.

Сравнение проведено со следующими документами принятого `main`:

- [Стратегия](../project/strategy.md): сценарно-независимое ядро, инфраструктурные модули/шаблоны, независимые исследовательские проекты, IaC и минимальная достаточность.
- [Roadmap](../project/roadmap.md): S0/S1/S1-D → S2 (Infrastructure Core) → S3 (подключаемые AI-возможности) → S4 (воспроизводимый шаблон среды).
- [Состояние](../project/state.md): функционально подтверждён S0→S1→S1-D Docker/Compose на `lab-test` в ограниченном объёме; S2–S4 не подтверждены реализацией.
- [Решения](../project/decisions.md): D-001 (`main` — принятый источник истины), D-010 (сценарно-независимая инфраструктура), D-011 (обычная сеть Docker Compose по умолчанию).

**Граница этого исследования:** не переопределять S3/S4 и не объявлять отказ от модулей и шаблонов принятым решением. Отдельные репозитории проектов — возможная реализация логического разделения, а не обязательное следствие.

## 2. Как сравнивать решения

Важно не смешивать пять уровней ответственности:

1. **Host bootstrap:** ОС, Docker, доступ, сеть, драйверы, исходное восстановление.
2. **Project/workspace environment:** инструменты разработчика, контейнерная среда, IDE, SDK, вычислительные ресурсы.
3. **Application deployment:** запуск сервисов, Compose-стеков, домены, обновления и health checks.
4. **Template distribution:** каталог готовых конфигураций или стеков, а не обязательно их запуск.
5. **Experiment/runtime execution:** бизнес-workflow, агентные задачи, ML-прогоны, тесты и пайплайны.

Один продукт может затрагивать несколько уровней, но не следует из этого, что он закрывает все их эксплуатационные требования. **Повторное развёртывание контейнеров ≠ восстановление данных БД ≠ воспроизводимость исследовательского результата.**

Маркировка: **[Факт]** — утверждение, подтверждаемое указанной официальной документацией; **[Анализ]** — вывод применительно к AI Lab; **[Гипотеза]** — требует локального эксперимента. Сведения о продуктовых возможностях актуальны на дату среза и могут измениться.

## 3. Карта существующих решений

| Решение | Основной объект управления | Способ воспроизведения | Заявленная/наблюдаемая граница | Источник |
| --- | --- | --- | --- | --- |
| NVIDIA AI Workbench | AI-проект и локальная/удалённая проектная среда | Git + `.project/spec.yaml` + опциональный Compose | Compose-сервисы одного проекта на одном хосте; данные томов отдельно | [1], [2], [3] |
| Dev Containers / DevPod | Рабочее окружение разработчика | `devcontainer.json` + provider | Не универсальная система эксплуатации приложений | [4] |
| Coder | Workspaces разработчиков/агентов | Terraform templates + provisioner | Центральный control plane; фокус на рабочих средах | [5], [6] |
| Coolify | Приложения, сервисы, deployment на подключённых серверах | Git/Dockerfile/Compose/API, MCP | Предполагает уже подготовленный сервер; часть состояния в control plane | [7], [8], [9] |
| Komodo | Docker-ресурсы, стеки, сборки и процедуры | Git TOML Resource Sync; Procedures | Управляет ресурсами/операциями, а не семантикой AI-эксперимента | [10], [11] |
| Portainer | Контейнеры/стеки и шаблоны | Application/Custom Templates | Каталог/администрирование контейнеров, не полная исследовательская методика | [12] |
| Docker Awesome Compose | Примеры одно- и многосервисных стеков | Каталог Compose-конфигураций в Git | В README прямо указано: для локальной разработки, не production | [13] |
| n8n Self-hosted AI Starter Kit | Готовый AI workflow-стек | Compose (n8n, Ollama, Qdrant, PostgreSQL) | В README обозначен как PoC, не production-ready | [14] |
| Dagger | Повторяемые операции сборки/проверки | Код модулей/функций и `dagger.toml` | Пайплайны и проверки, не сервисное окружение лаборатории целиком | [15] |
| MLflow Projects | Воспроизводимый запуск ML-кода | `MLproject`, entry points, окружение, параметры | Экспериментальный run, не bootstrap/общий deployment | [16] |

Формулировка «граница» в таблице означает **практическую предметную границу**, а не категорическое отсутствие дополнительных возможностей продукта.

## 4. Глубокое сравнение архитектурных кандидатов

### 4.1. NVIDIA AI Workbench — проект плюс управляемое окружение

- **Назначение [Факт].** Бесплатный инструмент для работы с локальными и удалёнными GPU-средами, включая изоляцию инструментов проекта, Git и контейнеры [1].
- **Контракт [Факт].** `.project/spec.yaml` описывает сборку и исполнение; `compose_file_path` указывает на Compose-файл внутри Git-репозитория. Секретные значения хранятся в локальном runtime, не в спецификации [2].
- **Runtime [Факт].** Compose-сервисы работают рядом с контейнером проекта на одном хосте. Состояние томов и БД автоматически не версионируется и требует отдельного backup [3].
- **Граница [Анализ].** Система хорошо подходит для воспроизводимого *проектного* окружения, но не устраняет требований AI Lab к исходному host bootstrap, данным и чистому восстановлению.
- **Для AI Lab [Гипотеза].** Может заменить часть самостоятельно планируемого слоя шаблонов проектных сред, особенно если нужны GPU и управление средами из GUI. Нужно проверить Linux/VMware, сетевые условия, работу с Codex и стоимость сопровождения.

### 4.2. Dev Containers + DevPod — стандарт прежде платформы

- **Назначение [Факт].** DevPod создаёт воспроизводимые среды на локальной машине, удалённом хосте или в облаке через providers с использованием `devcontainer.json` [4].
- **Контракт [Анализ].** Окружение описывается рядом с исходниками приложения; проект может поддерживать его независимо от инфраструктурного репозитория.
- **Граница [Анализ].** Хороший выбор для SDK/IDE/CLI/Codex, но сам по себе не заменяет эксплуатацию долгоживущих сервисов и данных.
- **Для AI Lab [Гипотеза].** Самый лёгкий первый кандидат для стандартизации среды *проекта*, если изоляции контейнера и команды запуска достаточно.

### 4.3. Coder — управляемый каталог рабочих пространств

- **Назначение [Факт].** Coder создаёт workspaces из Terraform templates; control plane управляет состояниями и жизненным циклом. В шаблоне учитываются persistent и ephemeral ресурсы [5], [6].
- **Граница [Анализ].** Это платформа рабочих сред, а не каталог бизнес-workflow или исследовательских методик. Появляются постоянный сервис управления, Terraform-шаблоны и эксплуатационные расходы.
- **Для AI Lab [Гипотеза].** Актуален при нескольких пользователях/агентах, множестве рабочих окружений, квотах или автоматическом выключении. Для одного тестового стенда — вероятно избыточен.
- **Оговорка.** Отдельные возможности жизненного цикла могут зависеть от редакции/лицензии; проверить перед выбором [6].

### 4.4. Coolify — развёртывание приложений, доступное агентам

- **Назначение [Факт].** Запуск приложений из Git, Dockerfile, образа или Compose на подключённом сервере [7].
- **Граница Git [Факт].** `Application` с Compose из Git использует файл репозитория. `Service` типа `Docker Compose Empty` хранит Compose внутри Coolify и не имеет Git-событий/ветки как источника [8].
- **Agent integration [Факт].** Встроенный MCP даёт агенту инструменты для просмотра, запуска, остановки и deployment; доступ ограничен токеном, командой и разрешениями. Сам MCP не является самостоятельным источником конфигурации [9].
- **Граница [Анализ].** Управляет deployment на уже существующем сервере, не заменяет инфраструктурный bootstrap и проверку сохранности данных. Не исключает конфигурационное состояние в собственном control plane.
- **Для AI Lab [Гипотеза].** Полезен, когда несколько независимых Git/Compose-проектов сложно сопровождать через CLI; не нужен только ради возможности «Codex выполняет deploy».

### 4.5. Komodo — инфраструктурные процедуры и Git-синхронизация

- **Назначение [Факт].** Управляет стеками, сборками, репозиториями, серверами, `Procedures` и `Resource Sync` [10], [11].
- **Граф [Факт].** `Procedures` имеют последовательные стадии с параллельными действиями; `Resource Sync` работает по TOML из Git и поддерживает порядок `after` между ресурсами [10], [11].
- **Граница [Анализ].** Это ближе к обсуждаемому `Deployment Workflow`, чем n8n, но его граф — граф *операций развертывания*, не прикладной агентный workflow.
- **Для AI Lab [Гипотеза].** Изучать при реальной необходимости координировать несколько стеков, серверов и операций. Пока обычный Compose проще.

## 5. Каталоги и примеры: не обязательно делать из каталога платформу

- **Docker Awesome Compose [Факт].** Хранит примеры Compose в Git, которые пользователь запускает сам. Авторы предупреждают, что это не production-конфигурации [13]. **[Анализ]** Подходящий образец лёгкого каталога, а не готовой эксплуатационной платформы.
- **n8n Self-hosted AI Starter Kit [Факт].** Композиция n8n + Ollama + Qdrant + PostgreSQL, по собственному README рассчитанная на PoC [14]. **[Анализ]** Это *кандидат в проект/пример стека*, не модуль инфраструктурного ядра.
- **Portainer Templates [Факт].** Позволяет распространять настраиваемые шаблоны контейнеров и стеков [12]. **[Анализ]** Полезен при потребности в UI каталога, которая пока не доказана.

Вывод: **шаблон в Git, управляющий интерфейс и запущенный экземпляр — три разные сущности**. Хранить каталог описаний можно без собственной службы каталога.

## 6. Применимость к AI Lab по этапам

| Этап | Принятое требование | Что найдено | Предварительная позиция |
| --- | --- | --- | --- |
| S0/S1/S1-D | Воспроизводимый bootstrap на поддерживаемом `lab-test` | Все рассмотренные платформы предполагают наличие части базовой среды | Оставить принятые скрипты/Compose; чужие платформы не подменяют существующие evidence |
| S2 | Модули, данные, секреты, диагностика и восстановление | Compose предоставляет минимальную основу; продукты deployment помогают позднее | Начать с одного репрезентативного сервиса и проверки data lifecycle; не добавлять control plane авансом |
| S3 | Подключаемая AI/runtime интеграция | Готовые Compose-стеки и проектные форматы | Делать опциональной, изолированной и удаляемой; поставщик/модель не обязательны |
| S4 | Воспроизводимый шаблон среды | AI Workbench, Dev Containers, Compose, каталоги | Сравнить способы *проектного* packaging, не придумывать собственный DSL до эксперимента |

**Проверка предложенной новой границы.** Независимые Git-репозитории AI-проектов совместимы с принятой стратегией «исследовательские проекты — потребители лаборатории». Однако стратегия также включает **проверенные повторно используемые модули и шаблоны как артефакты AI Lab**. Полный перенос всей reusable части в репозитории приложений стал бы *изменением* этой стратегии; данное исследование его не утверждает.

Возможная минимальная граница (не ADR):
- `ai-lab`: bootstrap, host/runtime baseline, скрипты проверки, общие инфраструктурные контракты — только по подтверждённой потребности;
- независимые проекты: собственные зависимости, Compose/Dev Container, код, runtime-workflows, тесты, данные и эксперименты;
- повторно используемые инфраструктурные заготовки: сначала обычные файлы/шаблоны с тестами в Git, место хранения решать по реальному повторному использованию.

## 7. Agent-authored deployment: вывод из сравнения

Рассматриваемый пример «агент через MCP создаёт workflow в n8n» содержит **два различных процесса**:

1. **Authoring/deployment:** агент готовит конфигурацию и вызывает инструменты.
2. **Runtime:** опубликованный n8n-workflow исполняет прикладную логику.

Вместо собственного «агентного deployment workflow engine» возможна комбинация:

`Project specification in Git → Codex (authoring) → review/tests → Compose / API / MCP (execution) → verification`.

[Анализ] Агент — удобный *автор изменений*, но не источник истины о целевой среде. Воспроизводимый результат должен жить в коде/конфигурации; фактический запуск и проверки должны быть доступны без исходной истории переписки с агентом. Это согласуется с D-001.

[Гипотеза] При наличии многих взаимозависимых deployments можно рассматривать Komodo или Dagger, но прежде измерить неудобство существующих Make/Compose.

## 8. Риски и неразрешённые вопросы

| Приоритет | Риск / открытый вопрос | Чем проверить |
| --- | --- | --- |
| P1 | Развёрнутый стек работает, но после удаления теряются данные | Persistent-volume backup/restore тест на одном сервисе; проверка данных после clean reset |
| P1 | Git отражает не всю фактическую конфигурацию (секреты, control-plane state, нажатия UI) | Инвентаризация входов; clean-machine replay только из зафиксированного контракта |
| P1 | Управляющая платформа сама становится новой точкой отказа | Удалить/повредить control plane в тесте; проверить recovery, ownership и exit path |
| P1 | Агентный deployment с избыточными правами | Минимальный scope MCP/API/SSH, аудит изменений, секреты вне Git, approval |
| P2 | Пересечение общего Docker/сети/портов нескольких проектов | Два Compose-проекта одновременно + stop/remove одного без повреждения другого |
| P2 | Лицензирование, редакции, обновления API и GPU-совместимость | Сверить версии/лицензии в момент практического выбора |
| P2 | Тяжёлая платформа экономит мало ручной работы на одном хосте | Измерить install/replay/cleanup effort против Compose baseline |

## 9. Предлагаемые следующие исследования и минимальный spike

**Не внедрять выбранную платформу по результатам одного документального обзора.**

Минимальный воспроизводимый эксперимент (`lab-test`, вне `main`, с последующим PR по результату):
1. Выбрать небольшой независимый проект: один HTTP-сервис + PostgreSQL + тестовая запись.
2. Зафиксировать версии, не-секретную конфигурацию, вводимые секреты, порты, volumes, команды `setup/verify/down`.
3. Развернуть существующим Compose без нового управляющего ПО (baseline); проверить API и чтение тестовой записи.
4. Остановить/поднять сервисы; выполнить controlled clean deployment и recovery данных из backup. Отдельно измерять «пустую установку» и «восстановление состояния».
5. Повторить на одном дополнительном инструменте **только если** обнаружен измеримый недостаток baseline (например, многопроектное управление, project IDE, agent MCP).
6. Зафиксировать время, ручные шаги, ошибки, число внешних компонентов, остаточное состояние после `down` и источник истины каждого параметра.

**Критерий решения:** дополнительный инструмент выбирается при доказанной пользе для конкретного потребителя. Если Compose + Git + Make покрывают текущие потребности — нового слоя нет.

## 10. Предварительные выводы (не ADR)

1. **[Факт]** Уже существуют готовые решения для Git-центричных project environments, deployment control planes и шаблонных стеков; нет необходимости автоматически создавать собственный каталог/DSL/оркестратор.
2. **[Анализ]** Для нынешнего масштаба AI Lab минимальный базовый путь — сохранять независимое ядро, а сценарные Compose/Dev Container/workflow размещать с проектами, когда это удобно.
3. **[Анализ]** NVIDIA AI Workbench — близкий по идее *проектных окружений* аналог; Coolify и Komodo — альтернативы для *эксплуатационного управления*, а не универсальные замены хостовой инфраструктуры.
4. **[Гипотеза]** Отложить сервисный каталог, оркестратор и обязательные Capabilities/Blueprints/Scenarios до появления хотя бы двух реальных независимых потребителей и повторяющихся задач.
5. **[Открыто]** Решить, какие reusable инфраструктурные шаблоны всё же принадлежат `ai-lab`, а какие — проектам; это потребует отдельного ADR, если изменится принятая стратегия.
