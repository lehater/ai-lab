**Рабочая ветка:** `proposal/multi-agent-e2e-first-slice`.

**Начальная точка:** [AGENTS.md](../../AGENTS.md) → [strategy](../project/strategy.md) → [state](../project/state.md) → [roadmap](../project/roadmap.md) → [decisions](../project/decisions.md).

## 1. Назначение и граница

Проверить на реальной небольшой задаче разработки, позволяет ли готовый агентный runtime (первый кандидат — OpenCode) делегировать ограниченную подзадачу локальной модели (Ollama) при выполнении основной задачи внешней моделью. Результат должен быть проверен автоматическими тестами, а конфигурация и свидетельства — доступны для повторного запуска.

Это **исследовательский потребитель** AI Lab, а не обязательный компонент Infrastructure Core. Работа отвечает потребности в первом реальном AI-потребителе, выделенной в [roadmap](../project/roadmap.md). Эксперимент не закрывает S2, S3 или S4 и не утверждает принятие OpenCode, конкретной модели, расширения или системы оркестрации.

Необходимые установки на начальном этапе могут быть ручными: сначала Proof of Value, затем решение о повторно используемом модуле и автоматизации через принятые механизмы (Ansible для новых host-managed компонентов; Compose для соответствующих сервисов). Не создавать заранее инфраструктурный модуль ради инструмента, полезность которого не проверена.

## 2. Что должно быть на входе и выходе

**Вход:** изолированный небольшой Git-проект с воспроизводимым дефектом и тестом, падающим на исходной ревизии; текст задачи; конфигурация доступных моделей/агентов; выбранная среда запуска.

**Выход:** минимальное исправление (diff), успешный запуск ранее падавшего теста и контрольных тестов, запись о том, какой агент и какая модель реально исполняли операции, команды запуска и очищенная от секретов трасса/журнал результатов.

**Основная проверяемая гипотеза:** штатные primary/subagents OpenCode позволяют вызвать локального read-only исследователя из облачного основного агента, а результат делегирования помогает основному агенту исправить дефект без написания собственного оркестратора.

**Контрольные вопросы:**
- Может ли OpenCode выполнить задачу отдельно с локальной и внешней моделью?
- Действительно ли происходит явное делегирование между двумя агентами с заданными моделями?
- Какие функциональные и ресурсные ограничения возникают?
- Достаточно ли штатного журнала/JSON-событий для воспроизведения и проверки?
- Что необходимо автоматизировать для будущего повторного использования?

## 3. Архитектура пилота (гипотеза, а не стек инфраструктуры)

```text
Task (small coding fix) -> OpenCode primary agent (external model)
                                   |
                                   +--> read-only subagent (Ollama local model)
                                   |        |
                                   |        +--> analysis / evidence
                                   |
                                   +--> code change -> tests -> result / trace
```

**Владение состоянием:** единственный пишущий агент — primary; локальному subagent выдавать только чтение. Без параллельной записи в одни файлы и Git. Внешняя модель получает только разрешённый для эксперимента код/контекст; секреты и приватные конфигурации исключить.

**Без обязательных дополнительных слоёв:** не реализовывать собственные Orchestrator, Model Gateway, Skills registry, Evaluator service, Observability server или HALO. OpenCode — лишь первый кандидат; Codex CLI — fallback-кандидат, если штатный runtime не выполняет необходимые функции. Oh My OpenCode Slim проверять отдельным контролируемым сравнением только при обнаружении конкретного ограничения.

## 4. Порядок выполнения и критерии перехода

### Gate 0 — preflight / выбор среды

1. Прочитать актуальный `main`, эту постановку, текущие открытые PR и реальные версии установленных инструментов. Проверить актуальные официальные инструкции OpenCode/Ollama и условия подключения внешнего провайдера (включая цену, ограничения подписки и лицензии). Исторические версии из исследований AI Lab не считать актуальными без проверки.
2. Выбрать **одну** среду первого прогона и записать выбор. При наличии GPU-ускоренного Ollama в WSL2 рекомендуется начать в WSL2; Ubuntu в VMware `lab-test` — отдельная принятая среда для инфраструктурной верификации. Если агент выполняется в VM, а Ollama в WSL2, проверить фактическую сетевую связность, маршруты и область доступности API. Не заявлять воспроизводимость на `lab-test` по результатам WSL2.
3. Определить реальные доступные модели и авторизацию. Локальную модель выбрать по подтверждённым ресурсам, контексту и tool-use совместимости. Внешнюю — по доступному легальному способу входа; не предполагать, что подписка эквивалентна универсальному API. Не хранить credential/token в Git.
4. В отдельной disposable рабочей области проверить доступность Ollama/API и безопасные ограничения OpenCode/агентов. Зафиксировать установленные версии, GPU/RAM/VRAM и способ подключения, не публикуя приватную сетевую конфигурацию.

**Gate 0 выход:** среда/версии/модели и ограничения записаны, оба backend доступны или обозначен конкретный BLOCKED. Пока — без разработки установщиков.

### Gate 1 — минимальный однопользовательский baseline

1. Подготовить изолированный маленький Python fixture: исходный commit, один заранее известный дефект, автоматические тесты, один из которых FAIL на исходном состоянии. Если fixture находится в AI Lab, держать его только в экспериментальном каталоге, а не в `modules/` или bootstrap; альтернативно использовать отдельный независимый репозиторий с зафиксированным SHA.
2. На **одинаковом исходном состоянии** выполнить небольшой coding-task штатным OpenCode с внешней моделью; сохранить diff, тесты, журнал и время.
3. Сбросить disposable fixture к исходному commit и выполнить ту же задачу OpenCode с локальной Ollama-моделью. Сохранить аналогичные свидетельства. Если локальная модель не справляется с необходимым tool-use, явно записать FAIL/BLOCKED и не подменять модель незаметно.
4. После каждого прогона независимо запустить тесты вне контекста агента. Успешное сообщение LLM без результатов тестов — не PASS.

**Gate 1 выход:** доказаны или опровергнуты вызовы двух backend и базовая работоспособность; известна оценка качества/латентности для этой задачи. Это **не** доказательство мультиагентности.

### Gate 2 — двухагентный E2E (минимальный MVP)

1. Объявить конфигурацию primary (внешняя модель) и локального read-only subagent (Ollama); конфигурация версионируемая, секреты вне репозитория.
2. На свежем состоянии fixture выполнить **одну** задачу, требующую явно вызвать subagent для анализа причины дефекта, после чего primary вносит исправление.
3. Подтвердить по фактическим событиям или logs: invocation primary, invocation subagent, идентификаторы моделей, передачу результата назад primary. Не заменять эту проверку «агент написал, что делегировал».
4. Независимо проверить diff и тесты. Сохранить конфигурацию, команду, результаты, очищенные события и известные ограничения.
5. Если штатные subagents не обеспечивают необходимое делегирование, зафиксировать воспроизводимый BLOCKED и сравнить альтернативу (Codex CLI или выбранное расширение). Не принимать новую зависимость без проявившейся проблемы.

**Gate 2 критерий приёмки:** одна задача проходит `task → primary → local subagent → primary → code diff → independent tests`; оба реальных backend подтверждены; не произошло утечки секретов или неразрешённой записи; есть пошаговая инструкция воспроизведения. Один успешный запуск подтверждает работоспособность, а не преимущество мультиагентной архитектуры.

### Gate 3 — передача результата / review

- Сформировать Markdown с фактическими версиями, командной последовательностью, средой, входным SHA, тремя вариантами прогонов (cloud baseline / local baseline / dual-agent), результатами и ограничениями; логировать `PASS`, `FAIL` или `NOT TESTED` строго по факту.
- Предоставить diff/fixture, тесты и обезличенные JSON/текстовые события. Не публиковать подписки, ключи, содержимое credentials, приватные исходники и сырые журналы без проверки.
- Предложить строго минимальную следующую итерацию по обнаруженной проблеме: автоматизировать необходимые опциональные компоненты (S3), либо оформить reusable template (S4), либо исследовать evaluation/расширение.
- Обновлять `docs/project/state.md` только при появлении фактического внедрения или проверок (с границами достоверности); `decisions.md` — только после утверждения решения владельцем. Не изменять `main` напрямую.

## 5. Проверяемая воспроизводимость

Для каждого реального запуска зафиксировать:

| Поле | Ожидание |
|---|---|
| Исходная ревизия fixture | Точный Git SHA и dirty/clean |
| Среда | OS, VM/WSL, CPU/RAM/GPU, доступность Ollama |
| Инструменты | Версия OpenCode/Ollama, режим запуска, конфигурация агентов |
| Модели | Реальные provider/model identifiers и локальная версия/тег, context setting при наличии |
| Вход | Неизменная формулировка задачи, исходно падающий тест |
| Процесс | Команды, событие делегирования, фактически вызванные модели, время |
| Выход | Diff, independent test output, ошибки/лимиты |
| Статус | PASS/FAIL/BLOCKED/NOT TESTED с объяснением и ограничениями |

Повторный запуск должен быть возможен **по инструкции** из исходной ревизии. Детерминизм текстового вывода LLM не гарантируется; воспроизводимыми должны быть процедура, исходная среда и независимые критерии оценки. Строгое автоматизированное развёртывание чистой VM/WSL — последующая отдельная задача.

## 6. Границы безопасности и ресурсов

- Изоляция на уровне disposable Git workspace, права на запись только у primary, без неконтролируемого запуска инструментов с повышенными привилегиями; пользовательское подтверждение для потенциально опасных действий.
- `Ollama` API не публиковать в LAN без явной необходимости. При межсредовом сетевом доступе проверить binding, firewall и реальные адреса, не отключать ограничения безопасности ради быстрого PASS.
- Не передавать приватные секреты, токены, профили прокси или внутренние файлы во внешние модели; сначала использовать полностью публичный disposable fixture.
- 24 ГБ VRAM на физическом GPU — не гарантия для любого контекста/модели. Проверять реальную память и производительность. VMware без GPU passthrough не считать эквивалентом GPU-ускоренного WSL2.
- Сохранение исходного Git checkout: не запускать опасный `git reset --hard` / cleanup в рабочем репозитории; только в созданной для эксперимента одноразовой копии.
- Платный API/превышение квоты и неожиданный исходящий трафик не должны запускаться без явного разрешения и понимания лимитов.

## 7. Что остаётся за рамками текущего PR/MVP

- Автоматическое развёртывание OpenCode, Ollama, Codex и каталог опциональных модулей через Ansible/Compose.
- Сравнение с Oh My OpenCode Slim без выявленной проблемы штатной оркестрации.
- Отдельные Promptfoo/Phoenix/Langfuse, HALO/DSPy/GEPA, автономный методист и контур улучшений.
- Multi-agent параллелизм, автоматический выбор провайдера, fallback в облако и самостоятельное изменение harness.
- Универсальная модель проекта, общий control plane, централизованные секреты и полная S2/S3/S4 приёмка.

**Поздняя стратегическая цель:** `Execution → Traces → Independent Evaluation → Change Proposal → Regression Tests → Owner-approved PR`. Возвращаться к ней после того, как реальный E2E даст проверяемые данные.

## 8. Инструкция следующему исполнителю (handoff)

1. Открыть **эту ветку**, не подменять её `main`. Затем прочитать `AGENTS.md`, принятые документы `main` и этот proposal. При расхождении признанных решений приоритет у `main`; любые изменения общей стратегии — отдельное предложение владельцу.
2. Проверить фактическую ветку и `git rev-parse HEAD`. Не трактовать содержание планового PR как уже проверенное.
3. Начать с Gate 0, далее Gate 1 → Gate 2; идти последовательно по критериям. Не заказывать установку инструментов и не объявлять PASS без доступа к фактической среде/свидетельствам.
4. Реализацию и доказательства добавлять в эту ветку небольшими коммитами; обновлять описание draft PR. Если работа разбивается на отдельные независимые PR, связывать их с этим proposal и сохранять последовательность.
5. Не сливать в `main` до независимого архитектурного review и операторской проверки, если она необходима.
